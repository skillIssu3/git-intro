Antes de empezar: la terminal en 6 comandos

¿Nunca has usado una terminal? Despliega esto
pwdTe dice en qué carpeta estás.
lsLista lo que hay en la carpeta actual.
cd carpetaEntra en una carpeta. cd .. sube un nivel y cd ~ vuelve a tu carpeta personal.
mkdir nombreCrea una carpeta nueva.
cat archivoMuestra el contenido de un archivo.
nano archivoEdita un archivo (o lo crea). Guardar: Ctrl+O y Enter. Salir: Ctrl+X.
Dos trucos: la tecla Tab completa nombres de archivos y carpetas, y la flecha hacia arriba recupera el comando anterior. Si algo da error, lee el mensaje: casi siempre dice qué pasa.

0. Solo Windows: instala WSL

Si usas Linux nativo, salta este paso. En Windows, abre PowerShell como administrador y ejecuta:

wsl --install -d Debian

Reinicia el equipo. Al abrir "Debian" te pedirá crear un usuario y una contraseña.

Si ya tenías WSL con Ubuntu, puedes seguir con Ubuntu: lo demás de la guía es igual.

Importante en WSL:
  • Trabaja siempre en tu carpeta personal (~/), nunca en /mnt/c.
  • La clave SSH (más abajo) se genera dentro de WSL, no en Windows.
  • Para VS Code, instala también la extensión WSL. Así podrás abrir carpetas con code .

1. Instalación de Git

Ejecuta en tu terminal el comando según la distribución seleccionada:

sudo apt update && sudo apt install -y git python3 python-is-python3

Con Debian en WSL es normal que salgan avisos como «Failed to connect to system scope bus»: no son errores.

Comprueba que está instalado (Git, y Python para los ejercicios):

git --version
python3 --version

2. Configurar identidad y opciones

Configura tu nombre y correo (el correo debe ser el de tu cuenta de GitHub), y dos opciones que evitan problemas más adelante:

git config --global user.name "Tu Nombre"
git config --global user.email "tu-email@ejemplo.com"
git config --global init.defaultBranch main
git config --global core.editor "nano"
  • user.name y user.email: quién firma tus commits.
  • init.defaultBranch main: la rama principal se llamará main.
  • core.editor "nano": el editor que Git abre si necesita que escribas un mensaje.
Usar otro editor (opcional)

Si prefieres otro editor, no ejecutes la última línea de arriba (core.editor "nano"). Copia en su lugar el comando del editor que quieras:

VS Code (en WSL necesita la extensión WSL y el comando code disponible en la terminal)

git config --global core.editor "code --wait"

Vim

git config --global core.editor "vim"

Neovim

git config --global core.editor "nvim"

Sublime Text

git config --global core.editor "subl -n -w"

Gedit

git config --global core.editor "gedit -w -s"

Kate

git config --global core.editor "kate --block"

Nano (el de la guía, por si quieres volver a él)

git config --global core.editor "nano"

Para ver qué editor tienes configurado ahora mismo:

git config --global core.editor

3. Generar la clave SSH y conectar con GitHub

¿Cómo funciona SSH por detrás? Lo explicamos en la presentación y en el README de git-intro.

Generar el par de claves
ssh-keygen -t ed25519 -C "tu-email@ejemplo.com"

Pulsa Enter a todo (ruta por defecto; la contraseña es opcional). Luego muestra tu clave pública:

cat ~/.ssh/id_ed25519.pub
  • Copia todo el texto que aparece en pantalla.
  • Ve a GitHub > Settings > SSH and GPG keys > New SSH key y pégala allí.
  • ¡ATENCIÓN: NO COPIES LA CLAVE PRIVADA (id_ed25519 sin el .pub)! COPIA ÚNICAMENTE LA CLAVE PÚBLICA (.pub).
Comprobar que funciona
ssh -T git@github.com

La primera vez te preguntará si confías en GitHub:

The authenticity of host 'github.com' can't be established.
Are you sure you want to continue connecting (yes/no)?

Es normal: es tu ordenador comprobando que GitHub es GitHub. Escribe yes. Si todo va bien, te saludará:

Hi TU_USUARIO! You've successfully authenticated, but GitHub does not provide shell access.
RECUERDA: Al clonar o vincular repositorios, usa siempre la URL SSH (git@github.com:...) en lugar de HTTPS.

Pasos para iniciar y subir tu primer proyecto

Paso 0: Crear el repositorio vacío en GitHub

Antes de tocar la terminal, ve a la web de GitHub y crea un repositorio nuevo (vacío, sin README ni .gitignore) y copia su URL SSH.

1. Crear la carpeta del proyecto e inicializar Git
mkdir -p ~/git
cd ~/git
mkdir nombre_que_quieres_para_tu_repositorio
cd nombre_que_quieres_para_tu_repositorio
git init
2. Crear README y primer Commit local
echo "# Mi Proyecto en Linux" > README.md
git status
git add .
git commit -m "Commit inicial"

git status te dice en todo momento qué ha cambiado y qué está preparado. Úsalo a menudo.

3. Vincular con GitHub y subir código
git remote add origin git@github.com:TU_USUARIO/mi-proyecto.git
git remote -v
git push -u origin main

Refresca la página del repositorio en GitHub: ahí está tu código.

Parte A: clonar y traer cambios (sin ramas)

1. Clonar el repositorio (usa la URL SSH)
git clone git@github.com:USUARIO/PROYECTO.git
cd PROYECTO

Cambia USUARIO y PROYECTO por los del repositorio que quieras clonar. El de la práctica está al final de esta pestaña.

2. Crear tu archivo con nano y escribir algo dentro
nano tunombre.txt

Escribe cualquier texto. Guarda con Ctrl+O y Enter, y sal con Ctrl+X.

3. Guardar y subir
git add tunombre.txt
git commit -m "Añado archivo de tunombre"
git push
4. Si el push es rechazado: traer los cambios de los demás
! [rejected] main -> main (fetch first)

No es un error grave: GitHub tiene commits que tú no tienes. Descárgalos con fetch, júntalos con merge y vuelve a subir:

git fetch
git merge origin/main
git push

fetch solo descarga lo nuevo y no toca tus archivos; merge lo junta con lo tuyo. Si se abre un editor pidiendo un mensaje de merge, guarda y cierra (en nano: Ctrl+O, Enter, Ctrl+X).

Parte B: ramas y Pull Request (Feature Branch Workflow)

Trabajar todos sobre main es peligroso: un fallo tuyo afecta a todos. La solución son las ramas.

5. Crear una rama independiente para cada nueva función
git checkout -b nueva_rama
6. Hacer cambios, guardarlos y subir tu rama
git add .
git commit -m "Añadida función X"
git push -u origin nueva_rama
7. Crear Pull Request desde la web de GitHub

Entra en el repositorio en GitHub y pulsa el botón verde Compare & pull request.

Rellena el título y la descripción. Un compañero revisa en Files changed y, si está bien, pulsa Merge pull request.

8. Volver a main y traer los cambios
git checkout main
git fetch
git merge origin/main

A practicar: ejercicios en equipo

Trabajaréis en grupos de 3 o 4 con un responsable. Las rondas, paso a paso y con botones de copiar, están en la pestaña 5. Ejercicios de esta guía, y también en el README del repositorio.

Simulador de resolución de conflictos de Merge

Cuando dos personas editan la misma línea, Git marca las diferencias en el archivo así. Usa las opciones de abajo para resolverlo:

<<<<<<< HEAD (Tus cambios locales)
const puerto = 8080; // Configuración servidor Linux
=======
const puerto = 3000; // Cambios remotos de tu compañero
>>>>>>> main

Y en la vida real

En VS Code aparecen estos mismos botones sobre el conflicto: Accept Current Change (lo tuyo), Accept Incoming Change (lo de tu compañero) y Accept Both Changes. Cuando lo tengas resuelto, sin ninguna marca <<<<<<<, ======= ni >>>>>>>:

git add archivo_con_conflicto
git commit -m "Resuelvo el conflicto"
git push

Si te lías, cancela el merge y vuelve a como estabas:

git merge --abort

Ejercicios en equipo: la batalla de luchadores

Grupos de 3 o 4 personas con un responsable. Cada uno crea su luchador y entre todos lo juntáis con Git. No hace falta saber programar: solo cambiar unos valores.

Usa los campos de Tus datos de arriba: tu nombre (de él sale el nombre de tu archivo, por ejemplo ana), tu usuario de GitHub (para el responsable) y el usuario del responsable (para quien no lo es). Si algo da error, lee el mensaje: casi siempre dice qué hacer. Versión completa en el README del repositorio.

Ronda 0: preparar el equipo

Un solo miembro del grupo hace de responsable. El resto espera al paso 5.

Responsable

1. Clona este repositorio
git clone git@github.com:skillIssu3/ejercicios-equipo.git
cd ejercicios-equipo
2. Crea tu repositorio vacío en GitHub

En la web de GitHub, crea un repositorio vacío y sin README en tu cuenta, llamado ejercicios-equipo.

3. Apunta tu copia a tu repo y súbela
git remote set-url origin git@github.com:TU_USUARIO/ejercicios-equipo.git
git remote -v
git push -u origin main
4. Invita a tu equipo

En tu repo de GitHub: Settings > Collaborators > Add people. Cada uno debe aceptar la invitación (llega por correo y en la campana de GitHub).

Resto del equipo

5. Cuando hayáis aceptado la invitación, clonad el repo del responsable (no el de la organización)
git clone git@github.com:USUARIO_DEL_RESPONSABLE/ejercicios-equipo.git
cd ejercicios-equipo

Rellena arriba el usuario de GitHub del responsable (pídeselo: no es el tuyo).

Todos

Abrid el proyecto en VS Code y comprobad que funciona
code .
python3 main.py

Debe decir «Todavía no hay nadie en miembros/».

Ronda 1: todos suben a la vez

Vais a añadir cada uno vuestro propio luchador, en su archivo. Nadie toca el de otro, así que no hay conflicto, pero Git os va a parar igualmente: es lo normal cuando varios suben a la vez.

1. Copia la plantilla con tu nombre (minúsculas, sin tildes)
cp miembros/_plantilla.py miembros/tunombre.py
2. Cambia los tres valores en VS Code

Abre tu archivo y cambia NOMBRE (el de tu luchador, puede ser un apodo), VIDA (máx. 30) y ATAQUE (máx. 8).

3. Comprueba que funciona
python3 main.py

Hacen falta al menos dos luchadores para pelear; mientras tanto te dirá que esperes rivales.

4. Guárdalo en Git y súbelo
git status
git add miembros/tunombre.py
git commit -m "Añado a tunombre"
git push
Todos a la vez, a la de tres. Los primeros en subir lo conseguirán. El resto verá:
! [rejected] main -> main (fetch first)
No es un error grave: el repositorio remoto tiene commits que tú no tienes. Hay que traerlos primero.
5. Trae lo de tus compañeros, júntalo con lo tuyo y vuelve a subir
git fetch
git merge origin/main
git push

git fetch solo descarga lo nuevo y no toca tus archivos; git merge origin/main lo junta con lo tuyo. Si se abre un editor pidiendo un mensaje de merge, guarda y cierra (en nano: Ctrl+O, Enter, Ctrl+X).

6. Ejecuta el programa
python3 main.py

¡Deberían pelear todos los luchadores del equipo!

Para pensar: ¿por qué el git merge no dio conflicto? Pista: mirad git log --oneline --graph.

Ronda 2: ramas y Pull Request

Hasta ahora habéis trabajado directamente sobre main. En equipos reales eso es peligroso: un fallo tuyo rompe el trabajo de todos. La solución son las ramas.

1. Asegúrate de estar al día
git fetch
git merge origin/main
2. Crea tu propia rama
git checkout -b tunombre-grito
3. Añade el grito de guerra

En miembros/tunombre.py, añade una línea al final con el grito de guerra de tu luchador:

GRITO = "¡Nadie me gana a piedra, papel o tijera!"

Es solo un ejemplo: pon el grito que quieras, siempre entre comillas.

4. Guarda y sube tu rama (no main)
git add miembros/tunombre.py
git commit -m "Añado grito de guerra de tunombre"
git push -u origin tunombre-grito
5. Abre el Pull Request en GitHub

Entra en el repo: verás un botón verde Compare & pull request. Ábrelo, ponle título y descripción, y créalo.

6. Revisión cruzada

Un compañero abre tu Pull Request, mira Files changed y, si está bien, pulsa Merge pull request.

7. Vuelve a main y trae los cambios
git checkout main
git fetch
git merge origin/main
python3 main.py

Cuando todos hayáis hecho merge de vuestros PR, main.py mostrará el grito de guerra de cada luchador antes del combate.

¡Y ya está! Podéis seguir jugando: subid la vida, probad otro ataque, inventad un luchador nuevo... siempre en una rama y con Pull Request.

Ronda 3: el torneo (al final de la charla)

Cuando os lo indiquen, vuestro luchador se apunta al torneo de todos los equipos: github.com/skillIssu3/torneo-luchadores. Las instrucciones (fork, rama y Pull Request) están en el README de ese repositorio.

Antes de empezar, ten al día el repo de ejercicios, porque de ahí copiarás tu luchador a luchadores/tuusuario.py:

git checkout main
git fetch
git merge origin/main
Los dos repositorios tienen que estar en la misma carpeta (por ejemplo ~/git).

Si algo sale mal

git statusQué está pasando ahora mismo. Es lo primero que hay que mirar.
git log --oneline --graphHistorial de commits en forma de árbol.
git remote -vA qué repositorio estás conectado.
git branchEn qué rama estás (la marcada con *).
git diffQué has cambiado y todavía no has preparado con add.
git merge --abortCancela un merge con conflictos y vuelve a como estabas.

Errores habituales

  • Permission denied (publickey): tu clave SSH no está bien subida a GitHub, o estás clonando con https:// en vez de git@github.com:.
  • Repository not found al clonar el repo de tu responsable: todavía no has aceptado su invitación.
  • CONFLICT ... Automatic merge failed: Git no sabe cuál de dos cambios en la misma línea elegir. Abre el archivo en VS Code, deja solo la versión buena (botones Accept...), y luego git add, git commit, git push. Si te agobias: git merge --abort.
  • Need to specify how to reconcile divergent branches: has usado git pull. En esta práctica usamos git fetch y luego git merge origin/main.
  • cannot run less o unable to execute pager 'less': tu sistema no tiene el programa less. Ejecuta una vez git config --global core.pager cat y repite el comando.
  • remote: Permission to ... denied: estás intentando subir al repo de la organización en vez del de tu responsable. Revisa git remote -v.

Comandos rápidos de búsqueda

git status - Muestra el estado del árbol de trabajo y archivos modificados.
git add . - Prepara todos los cambios para el commit.
git commit -m "mensaje" - Guarda los cambios preparados.
git push - Sube tus commits a GitHub.
git fetch - Descarga los cambios del remoto sin tocar tus archivos.
git merge origin/main - Junta lo descargado con tu rama.
git clone URL - Descarga un repositorio con todo su historial (usa la URL SSH).
git log --oneline --graph - Ver historial de commits de forma visual y condensada.
git diff - Muestra los cambios no preparados en tus archivos locales.
git restore archivo - Descarta los cambios no guardados de un archivo.
git remote -v - Muestra a qué repositorio remoto estás conectado.
git branch - Lista las ramas (la actual lleva un asterisco).
git checkout -b nombre - Crea una rama nueva y cambia a ella.
git checkout nombre - Cambia a una rama existente.
git merge --abort - Cancela un merge con conflictos y vuelve al estado anterior.
ssh -T git@github.com - Comprueba que tu clave SSH funciona con GitHub.
